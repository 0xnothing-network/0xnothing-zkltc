# NUSD utility for 0xPixel

## Active market (v2 implementation, redeployed with tokenomics v3)

The market built from `contracts/src/0xpixel/NusdNftMarketplaceV2.sol` was redeployed with tokenomics v3. The web uses it at `0xd219EfFe076B68934e212313C8d468b994d6e52E` (block `61141428`), settling in NUSD `0x69320A82ACCeC1b8A5EF59fd02b217e7ea4aEa19` (`contracts/deployments/v3-core.json:9-10`, `apps/web/lib/nusdMarketplace.generated.json:3-4,13`). Load these from the manifests rather than copying them. Integration guide: [developers/0xpixel.md](developers/0xpixel.md). Listings, offers, credits, pause rules and the UI flows below are unchanged. The fee changed:

- 0.1% of every sale is **burned** through `OracleNUSDv2.burn`, so NUSD supply falls and the reserve ratio rises.
- 0.4% is credited to the creator: the ERC-2981 receiver of the token (both 0xPixel collections return the artist). If a collection cannot name one, or names the market itself, the seller keeps that share.
- There is no platform fee, no fee recipient and no separate royalty rate; `quoteSale` returns `(burnAmount, creator, creatorFee, sellerProceeds)` and price = proceeds + creator fee + burn.

Pixel V1 was allowed by a separate `setCollectionAllowed` call after deployment (its PUSH0 bytecode cannot run in the repository's `paris` simulation EVM). The subgraph `pixel-nusd-market/1.1.0` also totals NUSD burned. NFT ownership is read from the collections through RPC; the old zkLTC marketplace index is no longer used. The v1 sections below describe the retired `0x188e…f377` market, which remains on chain. Statements below about a platform fee, a treasury, `platformFeeBps()` or reverting ERC-2981 lookups apply to v1 only.

## Three useful flows

1. **Buy and sell NFTs in NUSD.** The seller keeps the NFT until purchase. The buyer approves only the wallet shortfall and calls `buy(listingId, expectedPrice, maxWalletPayment)`. Changed prices or insufficient NFT approval revert without spending payment. The UI approves one NFT when necessary, not the entire collection.
2. **Escrow NUSD offers.** `makeOffer(collection, tokenId, price, expiresAt, maxWalletPayment)` locks the complete price until `expiresAt`, which must be in the future and at most `MAX_OFFER_DURATION` (30 days, 720 hours) ahead (`contracts/src/0xpixel/NusdNftMarketplaceV2.sol:59,167-172`); the UI accepts 1–720 hours (`apps/web/lib/nusdMarketplace.ts:77`). The current NFT owner can accept before expiry with an explicit minimum net proceeds. The maker can cancel at any time; anyone can trigger expiry. Refunds always belong to the maker, never the expiry caller. Offers can be made on any enabled existing NFT through the contract. The UI takes the target from a listing or from a manually entered collection and token id, which it checks with `collectionAllowed` and `ownerOf`.
3. **Recycle sale proceeds and refunds.** Seller proceeds, the 0.4% creator fee and cancelled/expired offer deposits become withdrawable NUSD credits. The active market has no platform fee. Credits are used before wallet tokens for purchases and offers. A user receiving 100 NUSD can spend it again without a withdraw/deposit round trip. If credits cover the full price, no ERC-20 approval is needed. `maxWalletPayment` prevents a changed credit balance from unexpectedly increasing wallet spending.

Credits are not automatically staked, lent, rewarded, or invested. Users can withdraw their entire credit to a chosen nonzero recipient with `withdrawNusd`. The UI withdraws to the connected wallet. Escrow only moves to a recipient's credit after sale or refund; it is not available for unrelated spending.

## Accounting, royalties and permissions

Where a bullet below mentions a platform fee or treasury, it describes v1. In the active v2 market, price = seller proceeds + 0.4% creator fee + 0.1% burn, and if no creator can be found the seller keeps the creator share instead of a revert (`contracts/src/0xpixel/NusdNftMarketplaceV2.sol:237-244,260-264`).

- `nusd.balanceOf(marketplace) >= escrowedNusd + totalCreditsNusd`. Without unsolicited donations, the amounts are equal. Deposits and withdrawals require exact token transfers; fee-on-transfer NUSD is rejected.
- v1: sale proceeds plus platform fee plus royalty exactly equal the price. v2: sale proceeds plus creator fee plus burn exactly equal the price. Overlapping recipients accumulate credit without double counting.
- v1 only: the deployment script uses an immutable 40 bps platform fee (0.4%) and explicitly configured treasury. The active v2 market has no platform fee or treasury. The contract constructor caps fees at 500 bps (5%); no owner can change fees or treasury after deployment.
- Collections are owner-allowlisted and must implement ERC-721/ERC-165. In v1, supported ERC-2981 royalty failures or excessive/invalid recipients revert instead of silently skipping creator payment; in v2 the seller keeps the creator share when no creator can be named. Royalties are computed on the sale price and credited in NUSD, the same settlement currency, as required by [ERC-2981](https://eips.ethereum.org/EIPS/eip-2981).
- The owner can allow/disable collections, pause trading and transfer ownership through a two-step process. Cancellation, offer expiry and NUSD withdrawals remain available during pause or collection disablement. There is no owner withdrawal of user balances, mint authority, token rescue or arbitrary call function.
- Credits belong to the credited address. A smart-contract seller, royalty receiver or treasury must be able to call `withdrawNusd` or market actions itself; an ERC-20-only payment splitter without arbitrary execution cannot claim these pull-payment credits. Review royalty recipients before allowing collections; use an executable treasury wallet. There is no permissionless forced withdrawal that could disrupt another user's planned credit-funded purchase.
- All financial actions have reentrancy protection and use [OpenZeppelin SafeERC20](https://docs.openzeppelin.com/contracts/5.x/api/token/erc20#SafeERC20). A failed NFT receiver reverts the complete sale.
- Active-listing/offer insertion and removal are O(1). Reads use offset/limit, capped at 100 contract-side and 24 UI-side. Pagination does not scan historical IDs. Concurrent changes can move entries between pages; refresh before signing.
- Frontend reads pin to a mined block and validate chain, immutable token and implementation marker. Signing is blocked on stale reads, pause or wallet/account/connector changes. The marker is a compatibility check, not cryptographic authentication of the code: configure only an independently verified deployment.
- Transactions use the existing confirmed-receipt flow, exact approvals and simulation. No automatic transaction retries. A replaced/cancelled transaction is not reported as a successful NFT trade.

## Deployment preparation

This section describes the v1 deployment tooling. The active v2 market was deployed by the tokenomics v3 script (`contracts/script/DeployV3Core.s.sol:123`, constructor `NusdNftMarketplaceV2(nusd, owner, collections)`) and is recorded as `nusdMarketplace` in `contracts/deployments/v3-core.json:10` and in `apps/web/lib/nusdMarketplace.generated.json`; do not rerun the v1 script to change it. Pixel V1 was allowed on it afterwards by `0xFi/scripts/deploy-v3.mjs:263`. The v2 tests are `NusdNftMarketplaceV2Test` (`contracts/test/unit/NusdNftMarketplaceV2.t.sol:12`); `NusdNftMarketplaceTest` below tests v1.

The approved v1 deployment is already recorded in `deployments/liteforge-testnet/nusd-marketplace.json`. From `0xFi/`, `node scripts/deploy-nusd-marketplace.mjs` now verifies that existing receipt and code without broadcasting a second deployment. For an undeployed environment it simulates first; `--broadcast` explicitly authorizes submission. Transaction hashes and public nonce/gas parameters are recorded before sending. An interrupted prepared transaction requires explicit `--submit-prepared`; `--replace-underpriced` only changes gas price after checking that the original transaction is not known and the nonce is unchanged. It reconstructs and verifies the original signed hash before replacing its preparation. These flags are operator recovery actions, not automatic retries. Neither the deployment record nor generated web configuration contains a private key.

Run from `contracts/` in PowerShell with Foundry installed:

```powershell
forge test --match-contract NusdNftMarketplaceTest -vv
forge build --sizes --skip DeployTestnet
$env:PIXEL_NUSD_MARKET_OWNER = '<reviewed owner address>'
$env:PIXEL_NUSD_MARKET_TREASURY = '<reviewed treasury address>'
$env:LITVM_RPC_URL = 'https://liteforge.rpc.caldera.xyz/infra-partner-http'
forge script script/DeployNusdMarketplace.s.sol:DeployNusdMarketplace --rpc-url $env:LITVM_RPC_URL
```

The last command is a dry run without `--broadcast`. The script pins the legacy v1 NUSD `0x5317e21aba902c6c7087a84457bc02fFe99604d1` (not the live v3 `OracleNUSDv2`), the 0xPixel V1/V2 collections and the 40 bps platform fee (`contracts/script/DeployNusdMarketplace.s.sol:15-18`); it refuses other chains. It uses Foundry's configured sender, not a private-key value embedded in source. Review bytecode, ownership, treasury, allowed collections, deployment simulation, and the NUSD/royalty interfaces before authorizing any broadcast. Use an encrypted keystore via Foundry's `--account` when subsequently deploying; never put keys in public environment variables, logs, command history or frontend files.

After a separately authorized, confirmed deployment:

1. Verify contract source and constructor inputs; confirm chain `4441`, `nusd()`, `IMPLEMENTATION_ID()`, owner, `BURN_BPS()`, `CREATOR_BPS()` and `collectionAllowed()` for both collections (v1 additionally had a treasury and `platformFeeBps()`). Do not configure a predicted dry-run address.
2. Publish the confirmed public deployment metadata into `apps/web/lib/nusdMarketplace.generated.json`, then restart/rebuild Next.js. The existing confirmed metadata is already configured. `NEXT_PUBLIC_PIXEL_NUSD_MARKETPLACE_ADDRESS=<confirmed address>` is an optional public override; empty values use the versioned deployment, while invalid/zero nonempty values disable trading. Do not replace the legacy contract address in native ABIs or APIs.
3. Smoke-test with small testnet amounts and two controlled wallets: list, edit price, cancel, buy, creator credit, withdraw, offer, cancel, re-use refund, accept and expiry. Confirm both NFT collection generations and Gallery deep links work. Exercise pause while checking cancellation/refunds/withdrawals remain available. These are operator actions, not transactions automatically broadcast by a UI redesign.
4. The main UI reads directly from RPC. The old subgraph does not index the new contract. `subgraphs/0xpixel-nusd-market` is a separate NUSD-only indexer (listings, offers, activity and mints from block 61141428; never merged with native trades; `subgraphs/0xpixel-nusd-market/subgraph.yaml:12,51,71`). It is deployed on Goldsky as `pixel-nusd-market/1.1.0`; the public endpoint is `nusdMarketGoldskyEndpoint` in `apps/web/features/fi/config/testnet.generated.json:42`, re-exported as `NUSD_SUBGRAPH_URL` in `apps/web/lib/nusdMarketplaceConfig.ts`. The web app's own activity route is internal and not a public endpoint; integrators query the subgraph directly. Listing prices, credits and pre-signing checks stay on RPC. Deploying the onchain contract does not publish the web application to a remote host; publish the tested web changes through the normal hosting pipeline when ready.

## Validation and limits

The contract suite covers NUSD accounting, 512-run price/refund fuzz tests, 24-step randomized refund/reuse sequences, real 0xPixel V2 royalties and inventory, stale listings, exact transfer enforcement, credit races, minimum proceeds, pause, pagination and callback reentrancy/atomic failure. Frontend tests cover strict amounts, bounded pinned reads, deployment gating, funding shortfalls, wallet changes, NFT approvals, offer acceptance, paused withdrawals/refunds and duplicate-click locking. These tests are not a third-party audit or live deployment validation.

This version does not add ERC-1155, auctions, lending against NFTs, bridging, automatic staking, speculative volume rewards, off-chain credit or automatic cross-market listing migration. Those require separate economic/security review rather than coupling user escrow to new risks.
